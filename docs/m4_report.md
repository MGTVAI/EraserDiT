# M4 验收与交付

复现：

```
python scripts/m4_measure.sh <clip> {N|A} 5 [gpu]        # N / A，写 results/m4/
python scripts/m4_side_by_side.sh <clip>                 # 源/B/N/A 四联对比
python scripts/acceptance.py --task-file tasks/acceptance_tasks.json
python scripts/m4_report.py                              # 汇总本文件的两张矩阵
```

`B` 是另一个代码库（`EraserDiT-baseline`，`baseline_runner.py --warmup --repeat 5`）。

## 1. 时间与显存

`t_load` 不计入端到端。`t_denoise`/`t_step`（每步中位数）/`t_vae`（解码）/`t_text`
（文本编码）单位秒；`t_io` 为窗口提交与编码写出之和。`t_warmup` 单列、不计入 `t_e2e`。

`A` 的预热是每进程一次性开销：`t_compile` 本身很短，51–88 s 的 `t_warmup` 里主要
是 Inductor 自动调优落在预热请求的首个前向。

## 2. 合格线

| 线 | 门槛 | `10268234` | `113000356` |
| --- | --- | --- | --- |
| `t_e2e(N)/t_e2e(B)` | ≤ 1.15 | 0.647 | 0.602 |
| `peak_reserved(N)/B` | ≤ 1.10 | 1.060 | 1.079 |
| `Δdenoise(A vs N)` | ≥ 15% | **+18.0%** | **+17.6%** |
| `Δe2e(A vs N)` | ≥ 10% | **+30.5%** | **+15.9%** |
| 整帧 SSIM/PSNR（A vs N） | ≥ 0.95 / ≥ 28 dB | 0.9887 / 39.65 | 0.9914 / 48.35 |

全部通过。

**随机性口径的错配，须说明**：`B` 用基线冻结的确定性口径，`N`/`A` 用快速口径，
两者不能直接相除得加速倍数（plan §6.4）。plan §6.2 记的 `10268234` 快速口径锚点为
318.0 s、`113000356` 为 675.6 s；以此为分母，`t_e2e(N)/t_e2e(B)` 分别是 **0.767** 和
**0.608**，同样远低于 1.15。本表报 0.647/0.602 是因为我实测的 `B`（377.0 s）比该锚点
高 18.6%——锚点取自另一个占用状态的窗口。两个分母下结论一致。

`10268234` 的 0.9895 / 40.55 落在这个带内，`113000356` 的 0.9925 / 48.75 高于它。

## 5. 连续任务验收

`tasks/acceptance_tasks.json` 是样例任务文件，4 个任务在**同一个常驻 pipeline** 里连续
执行，覆盖两种画幅、同画幅换 seed、再换回原画幅（后者用于确认 compile 签名被复用而
非重新编译）：

| 任务 | 素材 | 画幅 | seed |
| --- | --- | --- | --- |
| `clip1_portrait` | `10268234` | 1080×1920 | 42 |
| `clip2_landscape` | `113000356` | 1920×1080 | 42 |
| `clip2_landscape_other_seed` | `113000356` | 1920×1080 | 7 |
| `clip1_portrait_other_seed` | `10268234` | 1080×1920 | 7 |

`scripts/acceptance.py` 校验：输出齐全、输出两两不同（无状态串扰）、帧数与源一致、
非擦除区不低于 plan §6.2 的基线锚点（0.92 / 27 dB）。

> 结果见本文末尾「验收运行记录」。

### 运行记录（4 任务，一个常驻进程）

| 任务 | e2e | 净 e2e | denoise | 帧数 | 非擦除 SSIM/PSNR | 输出 md5 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `clip1_portrait` | 225.5 s | 171.5 | 150.5 | 120/120 | 0.9236 / 27.24 | `ea8387bc` |
| `clip2_landscape` | 346.3 s | 346.3 | 311.2 | 145/145 | 0.9818 / 35.70 | `af249051` |
| `clip2_landscape_other_seed` | 336.2 s | 336.2 | 301.4 | 145/145 | 0.9818 / 35.74 | `dd15149e` |
| `clip1_portrait_other_seed` | 172.5 s | 172.5 | 150.9 | 120/120 | 0.9238 / 27.24 | `d9ce8ef6` |

全部 PASS。要点：

- **输出两两不同**（4/4 唯一），同素材换 seed 后 md5 也变——seed 确实进到了采样器，
  没有跨任务状态串扰。
- **帧数与源严格一致，帧率被保留**（29.97 / 23.976023）。plan 标注过 `113000356`
  的源与 mask 帧率元数据不一致，这里没有擅自重采样。
- **预热只付一次**：首个任务 225.5 s，末个同素材任务 172.5 s，差额 53 s 就是预热，
  且只发生在任务 0。
- **两种画幅在同一进程内来回切换正常**（竖屏 → 横屏 ×2 → 竖屏）。
- **峰值显存升到 59.06 GiB**（单任务测量是 53.4–54.3）：常驻进程要同时留住两种画幅的
  编译图。仍低于基线的 60.0 GiB，但报告矩阵里的 `peak_reserved` 不能只看单任务数。

`--reuse results/acceptance_payload.json` 可对已有运行结果重跑校验，不必重跑推理。

## 6. 推荐配置与组合限制

推荐（详见 `docs/m3_report.md`）：

```
--attention-backend sage_attn --enable-torch-compile --warmup
```

- `auto` 在 A100（sm80）上实际选中 `sage_attn`，与本配置等价。
- **`--warmup` 是达标的必要条件**，不是可选优化：Inductor 自动调优 37–88 s 若不放进
  预热请求就会落在正式任务的首次前向里，去噪收益从 17% 掉到 10%，过不了 15% 线。
  代价是每进程一次性付出：把预热计回该次任务，`10268234` 仍是 206.8 s（优于 N 的
  243.8 s），`113000356` 是 433.2 s（**差于** N 的 410.9 s，因为它的调优更贵——2 窗口
  素材多一套形状）。**单任务冷启动场景不保证净收益，取决于素材形状数。**
- `torch.compile` 与 `operator_fusion_backend=triton` **互斥**（显式组合抛 `ValueError`；
  `auto` 降为空融合并以 `torch_compile_active` 为回退原因）。融合单项最好成绩是
  `sage_attn + 全融合` 的 +13.8% 去噪，不够 15%，不进推荐。
- `reduce-overhead` 编译模式比不编译更慢（`fullgraph=False` 下 CUDA graph 反复捕获），
  已否决。
- FP8 全系（`sage_fp8`、`fp8_w8a8*`）要求 sm89，A100 探针拒绝，不得进入任何推荐配置；
  `int8_w8a8_viditq` 依赖 `/root/viditq`，本机不存在，未实测。
